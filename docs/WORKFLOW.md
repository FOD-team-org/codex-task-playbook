# 진행 방식

시간표는 두지 않는다. 아래 기본 순서를 따르되, 담당자 답이 새로 나오거나 결과가 이상하면 그때그때 "상황별 할 일"로 간다. 단계마다 "내가 볼 것"이 사람이 검수하는 곳이다.

## 기본 순서

| 단계 | 할 일 | 내가 볼 것 | 넘어가는 기준 |
|---|---|---|---|
| 1. 파악 | 과제 설명과 자료 파일 목록을 본다. AGENTS.md는 기존 파일 아래에 이어 붙인다 | 과제가 무엇을 내라고 하는지, 정해 둔 스택·포트·시작 코드가 있는지 | 과제를 한 줄로 말할 수 있다 |
| 2. 요구사항 | 담당자 인터뷰(templates/INTERVIEW.md)를 하고 REQUIREMENTS.md를 쓴다 | 담당자 답마다 R이 있고 원문 그대로인가. 목표·결과물·맞다고 볼 표본이 적혔나 | 빠진 답 0, 안 만들 것 확인 |
| 3. 설계 | 빌드 1단계 지시를 넣는다(templates/BUILD_PROMPT.md). DESIGN.md를 받으면 계산 우선순위·기준값·방법 선택을 담당자에게 2~3안으로 확인한다(INTERVIEW.md 2차 왕복) | 방법 선택 표가 있으면 쓸 방법을 고른다. DESIGN.md의 흐름·요구사항 표·파일 지도·고장 지도. 파일 지도가 과제가 정한 폴더 구조와 같은가(정한 것이 없으면 frontend/·backend/ routes·services·repositories·db로 나뉘었나, 마이그레이션·Dockerfile·compose가 있나). 요구사항에 없는 기능(로그인, 대시보드·차트, 추가 API)이 있나 | 빠진 R 0, 없는 기능 0, 방법 선택 표가 있으면 쓸 방법을 골랐다 |
| 4. 구현 | 바꿀 점을 붙여 2단계 지시를 넣는다. 기다리는 동안 판단대기에 답하고 손 계산할 표본을 고른다 | DECISIONS.md 판단대기: `추천대로 두면`을 읽고 번호로 답한 뒤 이유를 한 줄 적는다 | Codex 완료 보고, 모든 판단대기에 답 |
| 5. 직접 확인 | 서버를 띄우고 미리보기에서 조건을 하나씩 바꿔 요약 줄이 바뀌는지 본다. 파일 내려받기가 있으면 엑셀로 연다 | 표본이 손 계산과 같은가. 제외 건수와 이유가 납득되나. 가려야 할 정보가 가려졌나. 한글이 깨지지 않나 | 눈으로 본 문제 목록 |
| 6. 검증 | 새 세션에서 검증 지시를 넣는다(templates/VERIFY_PROMPT.md) | 지적마다 반례 행을 직접 확인해 채택하거나 기각한다 | 결함 목록 |
| 7. 수정 | 같은 빌드 세션에 수정 지시와 판단 반영 지시를 한 메시지로 넣고, 5단계를 다시 한다 | 고친 결과가 표본과 같은가 | 테스트 통과, 표본 일치, 판단대기 0 |
| 8. 설명 준비 | DESIGN.md 설명 노트와 DECISIONS.md 문제 기록을 읽고 핵심 함수를 직접 연다. 검증 세션에 제출 전 연습 지시(VERIFY_PROMPT.md)를 넣어 사후 설명 체크 1~6에 한 번씩 답해 본다 | ASSUMPTIONS.md의 틀린 가정, DESIGN.md `## 바뀐 점`, 파일 지도에 없는 파일 | 아래 사후 설명 체크 통과 |
| 9. 제출 | README의 실행 명령을 처음부터 따라 해 본다. 필수 파일과 서버 종료를 확인한다. 역할이 있으면 역할마다 화면을 한 번씩 연다. docker가 있으면 README의 docker 명령으로 한 번 띄운다 | 명령대로 켜지고 테스트가 통과하나 | 제출 |

## 상황별 할 일

| 상황 | 할 일 |
|---|---|
| 담당자가 새 요구나 바뀐 기준을 말함 | REQUIREMENTS.md에 원문을 R로 더한 뒤, 같은 빌드 세션에 요구 추가 지시를 넣는다(BUILD_PROMPT.md) |
| 화면이나 결과가 이상함 | DESIGN.md 고장 지도에서 증상을 찾아 그 줄의 함수와 확인 명령부터 본다. 입력 행·기대·실제를 적어 수정 지시를 넣는다 |
| Codex가 판단대기를 올림 | `추천대로 두면`을 읽고 번호로 답한다. 모르면 담당자에게 묻는다. 답을 적은 뒤 판단 반영 지시를 넣는다 |
| 설계도가 요구와 다름 | 2단계 전이면 `바꿀 점`에 적는다. 구현 뒤면 수정 지시에 적는다. Codex가 DESIGN.md를 먼저 고친다 |
| 검증이 결함을 지적함 | 반례 행을 직접 열어 확인한 것만 채택한다. 기각한 것도 근거와 함께 `## 검증`에 남긴다 |
| 5분 넘게 진전이 없음 | 중단하고, 원인을 한 줄로 붙여 다시 지시한다 |
| 남은 시간이 15분 | 고치기를 멈추고 9단계(제출)로 간다 |

## 규칙
- Codex 세션은 빌드 1개와 검증 1개만 쓴다. 수정한 뒤에는 검증을 다시 열지 않고 회귀 테스트와 손 계산 표본으로 확인한다. 같은 내용을 여러 번 묻지 않는다.
- 보안·결제·운영처럼 틀리면 서비스에 문제가 생기는 판단만 Codex가 판단대기에 올리고 사람이 답한다. 답과 이유는 내 말로 적는다. 나머지 판단은 ASSUMPTIONS.md에서 훑어보고 틀린 것만 고친다.
- 단계를 마치면 Codex 보고의 커밋 명령을 그대로 친다(경로 지정, `git add .` 금지). 커밋 이력이 작업 과정 기록이 된다.

## 사후 설명 체크 — 문항 유형과 답이 있는 곳

문항은 내 제출물의 구체 사례에서 나온다. 답은 "결론 한 줄 → 이유(버린 대안) → 확인한 근거(명령·수치) → 약점과 그 영향 → 다음에 할 검증" 순서로 쓰고, 파일·함수 이름을 그대로 쓴다. 시간이 끝나면 쓰던 답이 확정되므로 결론부터 쓴다. 질문의 전제가 실제와 다르면 "실제로는 ~"로 바로잡는다.

1. 계산 방법(없으면 핵심 처리 규칙)을 고른 근거, 버린 대안, 한계 — DESIGN.md 계산 방법·방법 선택 표, 설명 노트 계산 방법·대안 비교
2. 데이터가 거치는 모듈과 상태 저장·소유 — 설명 노트 기능 하나의 계층·데이터 소유
3. 검증한 것과 가정한 것, 평가자가 확인할 경로 — 설명 노트 검증한 것과 가정한 것, DECISIONS.md 검증
4. 역할과 권한 경계 — 설명 노트 역할과 권한(역할이 하나면 경계값 처리로 대신 준비: REQUIREMENTS.md, ASSUMPTIONS.md)
5. 자료·조건이 바뀌면 더 할 검증, AI 결과를 믿은 근거 — 설명 노트 조건이 바뀌면, DECISIONS.md 검증 채택/기각
6. 문제 하나를 어떻게 발견하고 AI 진단을 어떻게 판단했나 — DECISIONS.md 문제 기록, AI가 틀렸던 순간

그 밖에 담당자에게서 끌어낸 요구와 처리한 코드 위치(REQUIREMENTS.md, DESIGN.md 요구사항 표), 만들지 않은 것과 이유(REQUIREMENTS.md)도 한 번씩 말해 본다.
