# 180분 진행 순서

| 시각(분) | 할 일 | 끝났다는 기준 |
|---|---|---|
| 0–10 | 과제 README와 data 파일 목록을 보고, AGENTS.md를 둔다 | 과제를 한 줄로 요약할 수 있다 |
| 10–35 | 담당자 인터뷰(templates/INTERVIEW.md)를 하고 REQUIREMENTS.md를 쓴다 | 항목 7개 이상, 안 만들 것 확인 |
| 35–40 | 빌드 지시를 넣는다 | Codex 시작 |
| 40–60 | 기다리는 동안 손 계산할 표본을 고르고, 판단대기 항목에 답과 이유를 적는다(필요하면 담당자에게 묻는다) | Codex 완료 보고 |
| 60–75 | 서버를 띄우고 미리보기에서 업로드·결과·다운로드를 직접 확인한다. CSV를 엑셀로 열고 표본과 대조한다 | 눈으로 본 문제 목록 |
| 75–85 | 새 세션에서 검증 지시를 넣는다 | 결함 목록 |
| 85–100 | 결함마다 채택 여부를 정하고, 수정 지시와 판단 반영 지시를 넣는다. 애매한 것은 담당자에게 다시 묻는다 | 수정 완료, 테스트 통과, 판단대기 0 |
| 100–115 | 60–75분 단계를 다시 한다 | 표본 일치 |
| 115–140 | 여유 구간. 남은 결함만 처리하고 새 기능은 넣지 않는다 | — |
| 140–165 | 핵심 함수를 직접 읽고 내 말로 설명을 DECISIONS.md에 적는다 | 아래 체크 통과 |
| 165–175 | README의 실행 명령을 처음부터 따라 해 본다. 필수 파일과 서버 종료를 확인한 뒤 제출한다 | 제출 |

## 규칙
- 165분에는 제출할 수 있는 상태를 만든다. 그 뒤로는 고치지 않는다.
- Codex 세션은 빌드 1개와 검증 1~2개만 쓴다. 같은 내용을 여러 번 묻지 않는다.
- 5분 넘게 진전이 없으면 중단한다. 원인을 한 줄로 붙여 다시 지시한다.

- 판단은 Codex가 판단대기에 올리고 사람이 답한다. 답과 이유는 내 말로 적는다. 서술형 답의 원본이 된다.

## 사후 설명 체크 (각 30초) — 답이 있는 곳
1. 담당자에게서 끌어낸 요구사항과 각각을 처리한 코드 위치 — DECISIONS.md 요구사항 → 구현
2. 경계값의 포함 여부와 그 이유 — 판단기록의 답·이유
3. 결과가 맞다는 근거(테스트, 손 계산, AI 검증 채택/기각) — 검증
4. AI가 틀렸던 순간과 잡아낸 방법 — 판단기록 "추천과 달랐나: 예", 검증 기각
5. 만들지 않은 것과 그 이유 — 만들지 않은 것
6. 기준이나 데이터 규모가 바뀌면 고칠 곳 — 판단기록 반영 줄, 한계
