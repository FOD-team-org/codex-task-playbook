# 진행 방식

시간표는 두지 않는다. 아래 기본 순서를 따르되, 담당자 답이 새로 나오거나 결과가 이상하면 그때그때 "상황별 할 일"로 간다. 단계마다 "내가 볼 것"이 사람이 검수하는 곳이다.

## 기본 순서

| 단계 | 할 일 | 내가 볼 것 | 넘어가는 기준 |
|---|---|---|---|
| 1. 파악 | 과제 설명과 자료 파일 목록을 본다. AGENTS.md는 기존 파일 아래에 이어 붙인다 | 과제가 무엇을 내라고 하는지, 정해 둔 스택·포트·시작 코드가 있는지. 정한 스택이 없으면 터미널에서 `npm view @nestjs/core version`으로 설치가 되는지 본다. 처음 보는 환경이면 Codex가 남긴 `## 환경` 표에서 막힌 칸과 설계에 주는 영향을 본다. 자료가 있으면 `## 자료 점검` 표에서 수가 0이 아닌 줄마다 처리 규칙이 있나 본다 | 과제를 한 줄로 말할 수 있다 |
| 2. 문제 정의 | 새 세션에서 문제 정의 지시(templates/PROBLEM_PROMPT.md)를 넣는다. Codex가 담당자에게 물을 문장을 주면 보내고, 답 앞에 `담당자:`를 붙여 그대로 넣는다. 바로 물을 수 있는 것은 답을 모아 한 메시지로 넣으면 왕복이 준다. 내 생각이 다르면 이유와 함께 말한다. 확정하면 이 세션을 닫는다 | 사실의 수치 하나를 직접 확인한다. 묶이지 않는 건수가 크면 공백이나 표기 차이 때문은 아닌지 본다. 가설이 담당자 말과 맞나. 갈림길마다 고른 쪽과 이유가 있나. `미확인`이 남은 쪽을 고르지 않았나. 추천이 과제 문장의 순서·범위를 바꾸지 않나. 기록이 없는 대상과 글로 적힌 칸의 제약을 다뤘나. 억지로 만든 문제나 새 기능이 끼지 않았나. 요구나 기준을 정한 담당자 답마다 R이 있고 원문 그대로인가. 담당자가 맡긴 갈림길은 내가 수를 보고 골랐나(못 고르면 `열림`). 추천을 그대로 받아도 왜 받았는지 한 줄 말한다 | 확정 문장을 내 말로 말할 수 있다. 부딪히는 목표의 순서, 풀렸다고 볼 수치와 표본, 안 풀 것이 정해졌다 |
| 3. 설계 | 새 세션에서 빌드 1단계 지시를 넣는다(templates/BUILD_PROMPT.md). Codex가 올린 고를 것에 답한다. DESIGN.md를 받으면 우선순위·기준값·방법 선택을 담당자에게 2~3안으로 확인한다. 예: "마감을 먼저 지키고 비용을 그다음에 줄이는 안(가)과 비용을 먼저 줄이는 안(나) 중 어느 쪽인가요?" 이해관계가 다른 사람이 있으면 양쪽이 받아들일 기준을 묻는다. 답은 REQUIREMENTS.md에 R로 더한다 | 문제와 목표·설계 결정·표본 따라가기가 PROBLEM.md의 결정과 맞나. 방법 선택 표가 있으면 쓸 방법을 고른다. DESIGN.md의 흐름, 요구사항 표(R과 화면 조건이 빠짐없이 있나), 고장 지도. 파일 지도가 과제가 정한 폴더 구조와 같은가(정한 것이 없으면 화면·서버·DB가 나뉘었나, 마이그레이션·배포 파일이 있나). 요구사항에 없는 기능(로그인, 대시보드·차트, 추가 API)이 있나 | 빠진 R 0, 없는 기능 0, 방법 선택 표가 있으면 쓸 방법을 골랐다 |
| 4. 구현 | 쓸 방법과 이상한 곳을 `바꿀 점`에 적어 2단계 지시를 넣는다. 기다리는 동안 판단대기에 답하고 손 계산할 표본을 고른다 | DECISIONS.md 판단대기: `추천대로 두면`을 읽고 번호로 답한 뒤 이유를 한 줄 적는다 | Codex 완료 보고, 모든 판단대기에 답 |
| 5. 직접 확인 | 서버를 띄우고 미리보기에서 조건을 하나씩 바꿔 결과가 바뀌는지 본다. 파일 내려받기가 있으면 엑셀로 연다 | 표본이 손 계산, DESIGN.md 표본 따라가기와 같은가. 처리되지 않은 건수와 이유가 납득되나. 결과의 최댓값·최솟값이 현실에서 말이 되나. 마지막 보고의 사람이 판단할 항목을 정했나. 가려야 할 정보가 가려졌나. 한글이 깨지지 않나 | 눈으로 본 문제 목록 |
| 6. 검증 | 새 세션에서 검증 지시를 넣는다(templates/VERIFY_PROMPT.md) | 지적마다 반례 행을 직접 열어 확인한 것만 채택하고, 기각한 것도 근거와 함께 `## 검증`에 V번호로 남긴다 | 결함 목록 |
| 7. 수정 | 같은 빌드 세션에 수정 지시와 판단 반영 지시를 한 메시지로 넣고, 5단계를 다시 한다 | 고친 결과가 표본과 같은가 | 테스트 통과, 표본 일치, 판단대기 0 |
| 8. 설명 준비 | 구현 뒤 코드를 고쳤으면 빌드 세션에 `explain-doc 스킬대로 EXPLAIN.md를 지금 코드에 맞춰 다시 써라.`를 넣는다. EXPLAIN.md를 읽고 핵심 함수를 직접 연다. 검증 세션에 제출 전 연습 지시(VERIFY_PROMPT.md)를 넣어 사후 설명 체크 1~6에 한 번씩 답해 본다 | ASSUMPTIONS.md의 틀린 가정, DESIGN.md `## 바뀐 점`, 파일 지도에 없는 파일 | 아래 사후 설명 체크 통과 |
| 9. 제출 | README의 실행 명령을 처음부터 따라 해 본다. 필수 파일과 서버 종료를 확인한다. 역할이 있으면 역할마다 화면을 한 번씩 연다. docker가 있으면 README의 docker 명령으로 한 번 띄운다 | 명령대로 켜지고 테스트가 통과하나. 마지막 보고의 배포 준비 확인에 실패·미확인이 남았나 | 제출 |

## 상황별 할 일

| 상황 | 할 일 |
|---|---|
| 문제 정의가 같은 자리를 돈다 | 열린 갈림길은 Codex 추천을 두고 확정한다. 설계와 구현에서 ASSUMPTIONS.md에 남는다 |
| 패키지 설치가 막힘 | Codex가 승인 요청으로 다시 실행하게 둔다. 그래도 막혀 Codex가 멈추고 알리면, 스택을 바꾸기 전에 왜 막혔는지 먼저 확인한다 |
| 담당자가 새 요구나 바뀐 기준을 말함 | 같은 빌드 세션에 요구 추가 지시를 넣는다(BUILD_PROMPT.md) |
| 결과의 값이 현실에서 말이 안 됨 | 넘으면 안 되는 기준을 담당자에게 묻고, 답을 요구 추가 지시로 넣는다. 정해 주지 않으면 내가 정하고 이유를 적는다 |
| 화면이나 결과가 이상함 | DESIGN.md 고장 지도에서 증상을 찾아 그 줄의 함수와 확인 명령부터 본다. 입력 행·기대·실제를 적어 수정 지시를 넣는다 |
| Codex가 판단대기를 올림 | `추천대로 두면`을 읽고 번호로 답한다. 모르면 담당자에게 묻는다. 답을 적은 뒤 판단 반영 지시를 넣는다 |
| 설계도가 요구와 다름 | 2단계 전이면 `바꿀 점`에 적는다. 구현 뒤면 수정 지시에 적는다 |
| 5분 넘게 진전이 없음 | 중단하고, 원인을 한 줄로 붙여 다시 지시한다 |
| 남은 시간이 15분 | 고치기를 멈추고 9단계(제출)로 간다 |

## 규칙
- Codex 세션은 문제 정의 1개, 빌드 1개, 검증 1개만 쓴다. 수정한 뒤에는 검증을 다시 열지 않고 회귀 테스트와 손 계산 표본으로 확인한다. 같은 내용을 여러 번 묻지 않는다.
- 판단대기에 답과 이유를 내 말로 적는다. 나머지 판단은 ASSUMPTIONS.md에서 훑어보고 틀린 것만 고친다.
- 단계를 마치면 Codex 보고의 커밋 명령을 그대로 친다. 커밋 이력이 작업 과정 기록이 된다.

## 사후 설명 체크 — 문항 유형과 답이 있는 곳

문항은 내 제출물의 구체 사례에서 나온다. 답은 "결론 한 줄 → 이유(버린 대안) → 확인한 근거(명령·수치) → 약점과 그 영향 → 다음에 할 검증" 순서로 쓰고, 파일·함수 이름을 그대로 쓴다. 시간이 끝나면 쓰던 답이 확정되므로 결론부터 쓴다. 질문의 전제가 실제와 다르면 "실제로는 ~"로 바로잡는다.

1. 방법(없으면 핵심 처리 규칙)을 고른 근거, 버린 대안, 한계 — EXPLAIN.md 2번, DESIGN.md 방법 선택·설계 결정
2. 데이터가 거치는 모듈과 상태 저장·소유 — EXPLAIN.md 3·4번
3. 검증한 것과 가정한 것, 평가자가 확인할 경로 — EXPLAIN.md 5번, DECISIONS.md 검증
4. 역할과 권한 경계 — EXPLAIN.md 6번
5. 자료·조건이 바뀌면 더 할 검증, AI 결과를 믿은 근거 — EXPLAIN.md 7번, DECISIONS.md 검증 채택/기각
6. 문제 하나를 어떻게 발견하고 AI 진단을 어떻게 판단했나 — EXPLAIN.md 8번, DECISIONS.md 문제 기록

그 밖에 처음 요청과 진짜 문제가 어떻게 달랐고 왜 그렇게 정했는지(PROBLEM.md), 담당자에게서 끌어낸 요구와 처리한 코드 위치(REQUIREMENTS.md, DESIGN.md 요구사항 표), 만들지 않은 것과 이유(REQUIREMENTS.md, PROBLEM.md)도 한 번씩 말해 본다.
