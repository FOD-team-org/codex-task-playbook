# 180분 진행 순서

| 시각(분) | 할 일 | 끝났다는 기준 |
|---|---|---|
| 0–10 | 과제 README와 data 파일 목록을 보고, AGENTS.md를 둔다 | 과제를 한 줄로 요약할 수 있다 |
| 10–35 | 담당자 인터뷰(templates/INTERVIEW.md)를 하고 REQUIREMENTS.md를 쓴다 | 항목 7개 이상, 안 만들 것 확인 |
| 35–40 | 빌드 1단계(설계) 지시를 넣는다 | DESIGN.md 완성 |
| 40–45 | DESIGN.md의 흐름·요구사항 표·고장 지도를 읽고, 바꿀 점을 붙여 2단계(구현) 지시를 넣는다 | 모든 R이 요구사항 표에 있다 |
| 45–60 | 기다리는 동안 손 계산할 표본을 고르고, 판단대기 항목에 답과 이유를 적는다(필요하면 담당자에게 묻는다) | Codex 완료 보고 |
| 60–75 | 서버를 띄우고 미리보기에서 업로드·결과·다운로드를 직접 확인한다. CSV를 엑셀로 열고 표본과 대조한다 | 눈으로 본 문제 목록 |
| 75–85 | 새 세션에서 검증 지시를 넣는다 | 결함 목록 |
| 85–100 | 결함마다 DESIGN.md 고장 지도로 원인 위치를 짚고 채택 여부를 정한 뒤, 수정 지시와 판단 반영 지시를 넣는다. 애매한 것은 담당자에게 다시 묻는다 | 수정 완료, 테스트 통과, 판단대기 0 |
| 100–115 | 60–75분 단계를 다시 한다 | 표본 일치 |
| 115–140 | 여유 구간. 남은 결함만 처리하고 새 기능은 넣지 않는다 | — |
| 140–165 | DESIGN.md의 흐름을 따라 핵심 함수를 직접 읽고, 내 말로 설명을 DECISIONS.md에 적는다 | 아래 체크 통과 |
| 165–175 | README의 실행 명령을 처음부터 따라 해 본다. 필수 파일과 서버 종료를 확인한 뒤 제출한다 | 제출 |

| 시각(분) | 볼 곳 | 확인할 것 | 통과 기준 |

| 35 | REQUIREMENTS.md | 담당자 답마다 R이 있고 원문 그대로인가. 목표·결과물·맞다고 볼 표본이 적혔나 | 빠진 답 0 |
| 40–45 | DESIGN.md 흐름·요구사항 표·파일 지도·고장 지도 | R이 전부 있나. 요구사항에 없는 기능(로그인, 대시보드·차트, 추가 API, DB)이 있나 | 빠진 R 0, 없는 기능 0 |
| 45–60 | DECISIONS.md 판단대기 | 항목마다 `추천대로 두면`을 읽고 번호로 답한 뒤 이유를 한 줄 적는다 | 모든 항목에 답 |
| 60–75 | 화면과 내려받은 CSV | 표본이 손 계산과 같은가. 연락처가 가려졌나. 엑셀에서 한글이 보이나 | 표본 일치 |
| 85–100 | 검증 결과 | 지적마다 반례 행을 직접 확인해 채택하거나 기각한다 | 채택분 수정, 회귀 테스트 추가 |
| 140–165 | ASSUMPTIONS.md, DESIGN.md `## 바뀐 점`, app/ 파일 목록 | 틀린 가정이 있나. 파일 지도에 없는 파일이 있나 | 고친 가정 표시, 설계와 코드 일치 |

## 규칙
- 165분에는 제출할 수 있는 상태를 만든다. 그 뒤로는 고치지 않는다.
- Codex 세션은 빌드 1개와 검증 1~2개만 쓴다. 같은 내용을 여러 번 묻지 않는다.
- 5분 넘게 진전이 없으면 중단한다. 원인을 한 줄로 붙여 다시 지시한다.

- 보안·결제·운영처럼 틀리면 서비스에 문제가 생기는 판단만 Codex가 판단대기에 올리고 사람이 답한다. 답과 이유는 내 말로 적는다. 나머지 판단은 ASSUMPTIONS.md에서 훑어보고 틀린 것만 고친다.

## 사후 설명 체크 (각 30초) — 답이 있는 곳
1. 담당자에게서 끌어낸 요구사항과 각각을 처리한 코드 위치 — DESIGN.md 요구사항 표, DECISIONS.md 요구사항 → 구현
2. 왜 이렇게 나눠 만들었나(흐름, 파일마다 맡은 일, 설계에서 바뀐 점) — DESIGN.md
3. 경계값의 포함 여부와 그 이유 — REQUIREMENTS.md, ASSUMPTIONS.md, 판단기록
4. 결과가 맞다는 근거(테스트, 손 계산, AI 검증 채택/기각) — 검증
5. AI가 틀렸던 순간과 잡아낸 방법 — 판단기록 "추천과 달랐나: 예", 고친 가정, 검증 기각
6. 만들지 않은 것과 그 이유 — 만들지 않은 것
7. 기준이나 데이터 규모가 바뀌면 고칠 곳 — DESIGN.md 파일 지도, 판단기록 반영 줄, 한계
