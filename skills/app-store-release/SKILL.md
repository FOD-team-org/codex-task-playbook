# 앱 스토어 출시

## 언제
- 첫 제출, 새 버전 제출, 구독·인앱 상품을 처음 붙일 때
- 심사 반려·메타데이터 누락 오류를 받았을 때
- 출시 전 QA를 할 때

## 제출 전 점검 (iOS)
- 유료 앱 계약이 활성 상태인지 본다. 팀 ID는 배포 인증서의 OU 값으로 확인한다.
- 첫 구독 상품은 앱 버전과 같은 심사 제출 묶음에 넣는다. 버전만 따로 제출하면 상품이 빠진다.
- MISSING_METADATA: 판매 지역(availability)을 가격보다 먼저 정한다. 상품 설명 글자 수 제한(짧다)을 확인한다.
- 새로 생긴 연령 등급 질문, 심사 담당 연락처, 콘텐츠 권리, 가격 일정을 채운다.
- iPhone 전용 앱이면 기기 설정과 전체 화면 요구 키를 맞춘다. 안 맞으면 iPad 화면 방향 오류로 업로드가 거절된다.
- 번들 표시 이름 외의 내부 이름은 ASCII로 둔다.

## 콘솔에서만 되는 것
아래는 API로 안 되거나 사람이 직접 해야 한다. user-task-guide 형식으로 안내하고, 화면 조작을 맡길 때는 console-cua-automation을 따른다.
- 앱 레코드 생성, 개인정보 라벨, 의료기기 여부 같은 신고 항목, 권한(entitlement) 신청
- 약관 동의, 심사 제출 버튼

## 심사 자료와 지침
- 심사 메모에 테스트 계정, 핵심 흐름, 실기기 녹화 링크를 넣는다.
- 권한 요청 전 안내 화면의 버튼은 중립 문구로 쓴다("계속" 등). "허용"을 유도하는 문구는 반려된다.
- 같은 개발자의 비슷한 앱은 기능·화면이 분명히 달라야 한다(스팸 지침).
- 메타데이터에 경쟁 앱 이름, "무료", 가격을 넣지 않는다.

## 심사 중·반려 뒤
- 반려 사유 원문은 스토어 콘솔의 메시지에만 있다. 메일 요약으로 판단하지 않는다.
- 심사를 취소하면 대기열 순서가 처음으로 돌아간다. 취소는 사람이 정한다.
- 반려되면 먼저 원인과 계획을 보고하고, 지적된 곳만이 아니라 같은 지침에 걸릴 곳을 앱 전체에서 찾는다. 수정은 승인 뒤에 하고, 다시 제출도 따로 승인을 받는다.
- 심사용 계정과 서버 환경은 심사 중에 바꾸지 않는다.

## 빌드와 설치
- 개발 전용 분기(디버그 메뉴, 시험 서버)가 출시 빌드에서 빠졌는지 본다.
- iOS 실기기 설치는 `xcrun devicectl device install app`.
- 안드로이드는 출시 빌드(R8 축소 포함)를 실기기에서 한 번 돌린다(android-device-smoke). 워크트리에는 서명 설정 파일이 없을 수 있다. 빌드 번호를 올린다. 서명이 달라 설치가 안 되면 기존 앱을 지우고 설치한다.
- 라이선스 테스터가 아닌 계정으로 결제를 시험하면 실제로 청구된다.
- 비공개 테스트 기간 요건(일수·인원)이 있으면 시작일과 끝나는 날을 운영 문서에 적는다.

## 업데이트 권장·강제
- 권장·강제 업데이트 기준 버전은 앱 코드가 아니라 서버 환경 값으로 둔다.
- 강제 업데이트는 사람이 명시적으로 강제하라고 했을 때만 켠다.

## QA
1. 디자인 시안과 시뮬레이터·에뮬레이터 캡처를 한 장에 나란히 놓고 대조한다(visual-output-qa).
2. iOS·안드로이드 모두 화면 전체를 쓰는지(여백·노치·내비게이션 바) 본다.
3. 처음 설치한 사용자처럼 실제 흐름을 처음부터 끝까지 걷는다. 개발 중 쌓인 상태로 보지 않는다.
4. 녹화가 필요하면 화면 녹화를 스크립트로 시작·종료해 길이를 맞춘다.
5. QA 계정을 따로 두고, 그 이름은 일반 가입에서 막는다.
- 외부 SDK는 줄인다. 오래된 패키지 고정 파일(Package.resolved 등)이 빌드를 막으면 원인을 확인하고 지운다.

## 하지 않는 것
- 승인 없는 심사 제출·취소, 반려 직후 승인 없는 수정
- 지적된 화면만 고치고 같은 문제를 앱 전체에서 찾지 않기
