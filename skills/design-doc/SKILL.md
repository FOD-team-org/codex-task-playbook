# 설계도

빌드를 시작하면 코드를 쓰기 전에 작업 폴더에 DESIGN.md를 쓴다. 사람이 읽고 길을 찾는 지도다.

PROBLEM.md가 있으면 먼저 읽는다. 확정 문장과 갈림길에서 고른 쪽을 설계의 기준으로 삼고, 다르게 설계해야겠으면 임의로 바꾸지 말고 사람에게 고르게 한다. PROBLEM.md의 수치는 문제 정의 때 센 값이다. 설계나 구현에서 다시 센 값이 다르면 사람이 고른 쪽은 그대로 두고 수치만 고치며, 무엇이 왜 달랐는지 `## 바뀐 점`과 마지막 보고에 적는다.

요구사항 표를 빼고 100줄 안으로 쓰고, 한 줄을 200자 안으로 둔다. 항목마다 `## 제목`을 두고, 표로 정한 항목은 표로 쓴다. 표는 머리행과 구분 줄이 있는 Markdown 표로 쓰고, 한 칸에 사실 하나만 둔다. 줄 수에 맞추려고 여러 사실을 한 줄로 누르지 않는다. 결과에 영향이 적은 항목을 덜 쓴다. 해당하지 않는 항목은 `해당 없음`으로 둔다. 과제 스택의 층 말고는 계층·추상화·확장 지점을 넣지 않는다.

지시가 "설계만"이면 DESIGN.md만 쓰고, 200자 넘는 줄을 세어 고친 뒤 멈춘다. 그렇지 않으면 이어서 구현한다.

## 항목
1. 문제와 목표: PROBLEM.md의 확정 문장과 풀렸다고 볼 기준을 옮기고, 그 기준을 화면의 어느 수치로 보이는지 적는다. PROBLEM.md가 없으면 누가 무엇을 하려고 쓰는지 한 문장으로 쓴다.
2. 흐름: 요청 하나가 지나가는 길을 화살표로 적는다. 핵심 흐름마다 한 줄씩 쓴다. 예: `GET /api/report?from&to` → report.controller.ts(입력 검사) → report.service.ts:summarize → report.repository.ts:findByPeriod → JSON 응답
3. 파일 지도: 파일마다 맡는 일을 한 줄로 적는다. 화면, 입력 검사·응답 모양, 계산·판정, 저장, 자료 적재, 배포 파일은 서로 다른 파일에 둔다. 계산·판정 함수는 req와 res를 받지 않게 만들어 따로 테스트할 수 있게 한다. 층 이름은 과제 스택에 맞춘다.
4. 데이터: 파일마다 행 하나가 무엇인지, 키, 정규화 방법, 묶기·중복 규칙, 저장 위치를 적고, 그 일을 하는 함수 이름을 적는다.
5. 방법 선택(결과를 좌우하는 방법을 고르는 일이 있을 때만): 목표의 우선순위(무엇을 먼저 지키고 무엇을 다음에 줄이는지), 꼭 지킬 제약, 방법 한 단락. 그 아래에 표 `후보 | 보장 수준(최적·근사·보장 없음) | 품질 지표 | 예상 계산 시간`을 3행(가장 단순한 기준선, 추천 방법, 이 과제에 쓸 수 있는 더 복잡한 방법이나 정확해)으로 쓰고 추천 한 줄을 붙인다. 고르지 않을 후보마다 버릴 이유를 한 줄 적는다. 사람이 설계 검토에서 고르고, 고르지 않으면 추천으로 진행한다. 사람이 고르지 않은 셋째 후보는 구현하거나 돌려 보지 않고 품질 지표에 `안 잼`으로 둔다. 앱에는 고른 방법 하나만 구현한다. 우선순위가 과제에 없으면 업무 상식으로 정하고 ASSUMPTIONS.md에 적는다.
6. 요구사항 표: `R번호 | 처리하는 파일:함수 | 확인하는 테스트 이름`. REQUIREMENTS.md의 R마다 한 줄씩 쓴다. 화면에서 바꾸는 조건은 `조건 | 화면 입력 id → 요청 값 → 쓰는 함수 | 재계산 테스트`로 한 줄씩 따로 쓴다.
7. API 표: `경로 | 입력 | 성공 응답 | 오류 응답`.
8. 위험 지점: 보안·결제·운영에 걸리는 곳과, 실제로 검사하거나 변환해서 막는 함수. 판단대기 번호(A1 등)가 있으면 함께 적는다. 사람이 답하기 전에는 추천안을 가장 작은 구현으로 넣는다. 원자적 저장이나 재시도처럼 코드가 커지는 안은 사람이 판단기록에서 고른 뒤에 넣는다.
9. 고장 지도: `증상 | 먼저 볼 곳(파일:함수) | 확인 명령`. 이 과제에서 생길 만한 증상을 5개 안팎으로 쓴다. 예: 합계나 평균이 틀림, 목록에서 행이 빠짐, 잘못된 입력이 통과하거나 맞는 입력이 400이 됨, 500이 남, 화면이 빔, 내려받은 파일이 깨짐. 먼저 볼 곳에는 그 증상이 지나는 함수를 흐름 순서(입력 검사 → 데이터 읽기·묶기 → 계산 → 출력)대로 적는다. 확인 명령에는 `|`를 쓰지 않는다. 표 안에서는 `\|`로 남아, 복사해 돌리면 테스트가 0개 돌고 통과처럼 보인다. 테스트 여러 개를 돌릴 때는 `--test-name-pattern=R3 --test-name-pattern=R4`처럼 옵션을 여러 번 쓴다. 패턴에는 R 번호까지 쓴다. `R`만 쓰면 모든 테스트가 돌아 어느 행인지 좁혀지지 않는다. 기본 스택의 확인 명령은 `npx tsc && node --test --test-name-pattern=R3 "backend/dist/test/**/*.test.js"` 꼴로 쓰고, 옵션은 경로 앞에 둔다. `npm test -- --test-name-pattern=R3`은 걸러지지 않아 전부 돈다.
10. 설계 결정: `결정 | 근거(PROBLEM.md의 사실·갈림길, R 번호) | 버린 안 | 틀렸을 때 나타나는 증상`. PROBLEM.md에서 고른 갈림길과 부딪히는 목표의 순서를 먼저 옮기고, 설계에서 새로 정한 결정을 더해 결과를 좌우하는 것만 쓴다. 정해진 스택, 화면 배치, 이름 짓기는 적지 않는다. PROBLEM.md와 REQUIREMENTS.md에 답이 없어 새로 정한 결정이 결과 수치를 바꾸면 judgment 스킬의 `결과를 좌우하는 가정`대로 행 앞에 `[결과]`를 붙이고, 버린 안 칸에 그 안이면 달라지는 수를 적는다.
11. 표본 따라가기: 자료의 실제 행으로 보통 경우 1건과 갈림길·예외에 걸리는 1~2건을 골라 `입력 행 → 거치는 판단 → 나와야 할 결과`를 적는다. 코드 실행 전에 과제와 자료로 따져 적고, 구현 뒤 테스트의 기대값으로 쓴다. 고른 해석에 따라 결과가 달라지면 달라지는 수도 적는다. 따져 보다가 설계가 막히면 설계를 먼저 고친다.
12. 바뀐 점: 처음에는 비워 둔다.

## 구현하는 동안
DESIGN.md는 고치지 않는다. 설계와 다르게 만든 점과 지도에 없던 고장 원인은 기억해 두었다가 끝낼 때 한 번에 반영한다.

## 끝낼 때
- 구현 중 달라진 점을 DESIGN.md 본문에 반영하고, `## 바뀐 점`에 무엇을 왜 바꿨는지 한 줄씩 적는다. 지도에 없던 고장 원인은 고장 지도에 더한다.
- DESIGN.md에 적은 파일:함수와 테스트 이름이 실제 코드에 있는지 한 번의 검색으로 확인한다. 다르면 문서를 코드에 맞춘다.
- 고장 지도의 확인 명령을 DESIGN.md에 적힌 그대로 한 명령에 묶어 차례로 돌리고, 각각 테스트가 1개 이상이면서 전체보다 적게 도는지 본다.
- 마지막 보고에 `DESIGN.md 대조: 함수 N개, 테스트 N개 일치`를 한 줄 넣는다.
