# 설계도

빌드를 시작하면 코드를 쓰기 전에 작업 폴더에 DESIGN.md를 쓴다. 사람이 읽고 길을 찾는 지도다. 60줄 안으로 쓰고, 요구사항에 없는 계층·추상화·확장 지점은 넣지 않는다. 지시가 "설계만"이면 DESIGN.md만 쓰고 멈춘다. 그렇지 않으면 이어서 구현한다.

## 항목
1. 목표: 누가 무엇을 하려고 쓰는지 한 문장.
2. 흐름: 요청 하나가 지나가는 길을 화살표로 적는다. 핵심 흐름마다 한 줄씩 쓴다. 예: `GET /api/report?from&to` → server.js 라우트(입력 검사) → rules.js:filterPeriod → rules.js:summarize → JSON 응답
3. 파일 지도: 파일마다 맡는 일을 한 줄로 적는다. 라우트(입력 검사·응답 모양), 데이터 읽기·정규화, 업무 규칙(계산·판정), 화면은 서로 다른 파일에 둔다. 업무 규칙 함수는 req와 res를 받지 않는 함수로 만들어 따로 테스트할 수 있게 한다.
4. 데이터: 파일마다 행 하나가 무엇인지, 키, 정규화 방법, 묶기·중복 규칙을 적고, 그 일을 하는 함수 이름을 적는다.
5. 요구사항 표: `R번호 | 처리하는 파일:함수 | 확인하는 테스트 이름`. REQUIREMENTS.md의 R마다 한 줄씩 쓴다.
6. API 표: `경로 | 입력 | 성공 응답 | 오류 응답`.
7. 위험 지점: 보안·결제·운영에 걸리는 곳과, 실제로 검사하거나 변환해서 막는 함수. 판단대기 번호(A1 등)가 있으면 함께 적는다. 사람이 답하기 전에는 추천안을 가장 작은 구현으로 넣는다. 원자적 저장이나 재시도처럼 코드가 커지는 안은 사람이 판단기록에서 고른 뒤에 넣는다.
8. 고장 지도: `증상 | 먼저 볼 곳(파일:함수) | 확인 명령`. 이 과제에서 생길 만한 증상을 5개 안팎으로 쓴다. 예: 합계나 평균이 틀림, 목록에서 행이 빠짐, 잘못된 입력이 통과하거나 맞는 입력이 400이 됨, 500이 남, 화면이 빔, 내려받은 CSV가 깨짐. 먼저 볼 곳에는 그 증상이 지나는 함수를 흐름 순서(입력 검사 → 데이터 읽기·묶기 → 계산 → 출력)대로 적는다. 확인 명령에는 `|`를 쓰지 않는다. 표 안에서는 `\|`로 남아, 복사해 돌리면 테스트가 0개 돌고 통과처럼 보인다. 테스트 여러 개를 돌릴 때는 `--test-name-pattern=R3 --test-name-pattern=R4`처럼 옵션을 여러 번 쓴다. 패턴에는 R 번호까지 쓴다. `R`만 쓰면 모든 테스트가 돌아 어느 행인지 좁혀지지 않는다.
9. 바뀐 점: 처음에는 비워 둔다.

## 구현하는 동안
- 설계와 다르게 만들어야 하면 코드보다 DESIGN.md를 먼저 고치고, `## 바뀐 점`에 무엇을 왜 바꿨는지 한 줄 적는다.
- 테스트가 실패하거나 오류가 나면 고장 지도에서 출발한다. 원인을 찾았는데 지도에 없던 곳이면 그 줄을 더한다.

## 끝낼 때
- DESIGN.md에 적은 파일:함수와 테스트 이름이 실제 코드에 있는지 검색해 하나씩 확인한다. 다르면 문서를 코드에 맞춘다.
- 고장 지도의 확인 명령을 DESIGN.md에 적힌 그대로 하나씩 돌려, 테스트가 1개 이상이면서 전체보다 적게 도는지 본다.
- 마지막 보고에 `DESIGN.md 대조: 함수 N개, 테스트 N개 일치`를 한 줄 넣는다.
