# 설계도

빌드를 시작하면 코드를 쓰기 전에 작업 폴더에 DESIGN.md를 쓴다. 사람이 읽고 길을 찾는 지도다. 60줄 안으로 쓰고, AGENTS.md 스택의 층(화면·라우트·서비스·저장소·DB) 말고는 계층·추상화·확장 지점을 넣지 않는다. 지시가 "설계만"이면 DESIGN.md만 쓰고 멈춘다. 그렇지 않으면 이어서 구현한다.

## 항목
1. 목표: 누가 무엇을 하려고 쓰는지 한 문장.
2. 흐름: 요청 하나가 지나가는 길을 화살표로 적는다. 핵심 흐름마다 한 줄씩 쓴다. 예: `GET /api/report?from&to` → routes/report.js(입력 검사) → services/report.js:summarize → repositories/report.js:findByPeriod → JSON 응답
3. 파일 지도: 파일마다 맡는 일을 한 줄로 적는다. 화면(frontend/), 라우트(입력 검사·응답 모양), 서비스(계산·판정), 저장소(DB 읽기·쓰기), 마이그레이션·CSV 적재, 배포 파일(Dockerfile·compose)은 서로 다른 파일에 둔다. 서비스 함수는 req와 res를 받지 않게 만들어 따로 테스트할 수 있게 한다. DB는 저장소만 부른다.
4. 데이터: 파일마다 행 하나가 무엇인지, 키, 정규화 방법, 묶기·중복 규칙, 적재하는 테이블을 적고, 그 일을 하는 함수 이름을 적는다.
5. 계산 방법(배정·편성·경로·추천처럼 계산이 핵심일 때만): 목표의 우선순위(무엇을 먼저 지키고 무엇을 다음에 줄이는지), 꼭 지킬 제약, 방법 한 단락. 그 아래에 방법 선택 표 `후보 | 보장 수준(최적·근사·보장 없음) | 품질 지표 | 예상 계산 시간`을 2~3행(가장 단순한 기준선, 추천 방법, 필요하면 정확해)으로 쓰고 추천 한 줄을 붙인다. 사람이 설계 검토에서 고르고, 고르지 않으면 추천으로 진행한다. 구현은 고른 방법 하나만 한다. 우선순위가 과제에 없으면 업무 상식으로 정하고 ASSUMPTIONS.md에 적는다.
6. 요구사항 표: `R번호 | 처리하는 파일:함수 | 확인하는 테스트 이름`. REQUIREMENTS.md의 R마다 한 줄씩 쓴다. 화면에서 바꾸는 조건은 `조건 | 화면 입력 id → 요청 값 → 쓰는 함수 | 재계산 테스트`로 한 줄씩 따로 쓴다.
7. API 표: `경로 | 입력 | 성공 응답 | 오류 응답`.
8. 위험 지점: 보안·결제·운영에 걸리는 곳과, 실제로 검사하거나 변환해서 막는 함수. 판단대기 번호(A1 등)가 있으면 함께 적는다. 사람이 답하기 전에는 추천안을 가장 작은 구현으로 넣는다. 원자적 저장이나 재시도처럼 코드가 커지는 안은 사람이 판단기록에서 고른 뒤에 넣는다.
9. 고장 지도: `증상 | 먼저 볼 곳(파일:함수) | 확인 명령`. 이 과제에서 생길 만한 증상을 5개 안팎으로 쓴다. 예: 합계나 평균이 틀림, 목록에서 행이 빠짐, 잘못된 입력이 통과하거나 맞는 입력이 400이 됨, 500이 남, 화면이 빔, 내려받은 CSV가 깨짐. 먼저 볼 곳에는 그 증상이 지나는 함수를 흐름 순서(입력 검사 → 데이터 읽기·묶기 → 계산 → 출력)대로 적는다. 확인 명령에는 `|`를 쓰지 않는다. 표 안에서는 `\|`로 남아, 복사해 돌리면 테스트가 0개 돌고 통과처럼 보인다. 테스트 여러 개를 돌릴 때는 `--test-name-pattern=R3 --test-name-pattern=R4`처럼 옵션을 여러 번 쓴다. 패턴에는 R 번호까지 쓴다. `R`만 쓰면 모든 테스트가 돌아 어느 행인지 좁혀지지 않는다.
10. 바뀐 점: 처음에는 비워 둔다.

## 구현하는 동안
- DESIGN.md는 고치지 않는다. 설계와 다르게 만든 점과 지도에 없던 고장 원인은 기억해 두었다가 끝낼 때 한 번에 반영한다.
- 테스트가 실패하거나 오류가 나면 고장 지도에서 출발한다.

## 끝낼 때
- 구현 중 달라진 점을 DESIGN.md 본문에 반영하고, `## 바뀐 점`에 무엇을 왜 바꿨는지 한 줄씩 적는다. 지도에 없던 고장 원인은 고장 지도에 더한다.
- DESIGN.md에 적은 파일:함수와 테스트 이름이 실제 코드에 있는지 한 번의 검색으로 확인한다. 다르면 문서를 코드에 맞춘다.
- 고장 지도의 확인 명령을 DESIGN.md에 적힌 그대로 한 명령에 묶어 차례로 돌리고, 각각 테스트가 1개 이상이면서 전체보다 적게 도는지 본다.
- 마지막 보고에 `DESIGN.md 대조: 함수 N개, 테스트 N개 일치`를 한 줄 넣는다.
- DESIGN.md 맨 아래에 `## 설명 노트`를 35줄 안으로 쓴다(60줄 제한에 세지 않는다). 사후 설명 문항은 제출물의 구체 사례를 묻는다. 사람이 이 노트만 읽고 답할 수 있게 항목마다 실제 파일:함수와 수치를 넣는다.
  - 계산 방법: 무엇을 먼저 지켰고 왜 이 방법인지, 공평이나 이용자 편의를 위해 넣은 장치(없으면 적지 않고, 적으려고 새로 넣지 않는다), 이 방법의 약점. 항목 5를 쓰지 않은 과제면 핵심 처리 규칙(거르기·묶기·집계 기준)을 왜 그렇게 정했는지와 약점을 적는다.
  - 대안 비교: 더 단순한 대안 하나(예: 정렬해서 차례로 채우기)를 같은 자료·기본 조건으로 명령 한 번에 돌려, 고른 방법과 핵심 수치 2~3개를 표로 비교한다. 대안은 앱 코드에 넣지 않는다. 항목 5를 쓰지 않은 과제면 돌리지 않고, 고르지 않은 처리 규칙 하나와 그 이유를 한 줄로 적는다.
  - 기능 하나의 계층: 조건 하나를 바꿨을 때 화면 입력 → 요청 → 라우트 → 서비스 → 저장소 → DB 테이블을 파일:함수로 차례로 적고, 층마다 맡은 일을 한 줄로 적는다. 이렇게 나눈 이유(화면은 계산하지 않는다, DB는 저장소만 부른다)를 한 줄 붙인다.
  - 데이터 소유: 표마다 어디서 채워지고(CSV 적재, 화면 입력) 누가 바꿀 수 있는지, 저장하지 않는 것.
  - 역할과 권한(역할이 있을 때만): 역할마다 보고 바꿀 수 있는 것과 서버에서 막는 파일:함수.
  - 검증한 것과 가정한 것: 테스트·손 계산으로 확인한 것과 확인하지 못해 가정한 것을 나눠 적고, 평가자가 직접 확인할 명령이나 화면 경로를 항목마다 붙인다.
  - 조건이 바뀌면: 자료나 조건이 바뀔 때 다시 돌릴 테스트와 달라질 수 있는 수치.
