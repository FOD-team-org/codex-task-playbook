# 브랜치·PR·병합 반복

## 언제 쓰나
- 사람이 그 저장소에서 push·PR·병합을 상시로 맡겼고, 그 범위가 프로젝트 지침이나 기록에 적혀 있을 때만 쓴다.
- 상시 위임이 없으면 operating-principles대로 push·병합마다 승인을 받는다.
- push가 곧 운영 배포인 저장소(main 자동 배포 등)는 상시 위임이 있어도 배포 직전에 묻는다.

## 시작 전
- 지금 폴더와 브랜치가 맞는지 확인한다. 이름이 비슷한 폴더(v1·v2, 복사본)를 헷갈린 적이 있다.
- 프로젝트 지침의 브랜치·PR 규칙을 매 기능마다 다시 읽는다.
- 기능마다 새 브랜치를 만든다.

## 순서
1. 테스트를 먼저 쓴다(실패 확인).
2. 구현한다.
3. 검증한다: 바꾼 범위의 테스트, 타입 검사, 린트.
4. 커밋한다. 커밋 하나에 변경 하나.
5. push하고 PR을 연다. 본문에 무엇·왜·검증 결과를 쓴다.
6. 자동 리뷰가 달릴 시간(예: 10분)을 기다린 뒤 코멘트를 확인한다.
7. 지적이 하나라도 있으면 고쳐서 다시 올리고 6으로 간다.
8. 지적이 없고 검사가 통과하면 병합한다.
9. 체크리스트·진행 문서를 갱신하고 다음 기능으로 간다.

## 규칙
- 커밋 작성자 정보는 훅·설정이 정한 대로 둔다. 훅을 건너뛰는(`--no-verify`) 커밋을 하지 않는다.
- 테스트가 통과하기 전에는 PR을 올리지 않는다.
- 메인 브랜치 병합은 테스트와 검수를 통과한 뒤에만 한다.
- 구현한 에이전트와 병합하는 쪽을 나눌 수 있으면 나눈다. 구현 에이전트는 커밋하지 않고, 메인이 검수 승인 뒤 커밋한다(multi-ai-review).

## 하지 않는 것
- 상시 위임 없는 push·병합, 강제 push, 훅 건너뛰기
- 리뷰 코멘트를 보지 않고 병합
