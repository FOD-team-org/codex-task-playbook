# 빌드 지시 (새 세션)

괄호 안은 과제에 맞게 채웁니다. 문제 정의를 확정한 뒤 새 세션에서 시작합니다.

## 1단계: 설계 (첫 메시지)

```
과제 설명은 (과제 파일), 문제 정의는 PROBLEM.md, 요구사항은 REQUIREMENTS.md, 자료는 (자료 폴더)에 있다.
design-doc 스킬로 DESIGN.md만 쓰고 멈춰라. 코드는 아직 쓰지 않는다.
요구사항에 답이 없는 판단은 judgment 스킬로 나눠라.
응답 끝에 설계에서 내가 고를 것을 3개 안으로 적어라. 항목마다 추천과, 추천대로 두면 담당자가 무엇을 보게 되는지를 한 문장으로 쓴다. 없으면 "없음"이라고 쓴다.
```

더 의논할 것이 있으면 같은 세션에 "코드는 쓰지 말고 DESIGN.md만 고쳐라"를 붙여 말합니다.

## 2단계: 구현 (같은 세션)

```
DESIGN.md대로 구현하고, AGENTS.md의 `끝내기 전`을 차례로 마쳐라. 바꿀 점: (없으면 "없음")
```

## 요구 추가 지시 (같은 빌드 세션)

담당자가 새 요구나 바뀐 기준을 말하면, REQUIREMENTS.md에 원문을 R로 더한 뒤 넣습니다.

```
REQUIREMENTS.md에 R?가 추가됐다(또는 바뀌었다). 이 항목만 반영하고 다른 부분은 바꾸지 마라.
먼저 DESIGN.md의 흐름·요구사항 표·고장 지도에서 바뀌는 줄을 고치고 `## 바뀐 점`에 한 줄 적은 뒤 구현하라.
R?의 테스트를 추가하고 전체 테스트를 다시 돌려라.
```

## 수정 지시 (같은 빌드 세션)

```
다음 결함만 bug-fix 스킬로 고쳐라. 다른 부분은 바꾸지 마라.
- (결함 1: 입력 행 / 기대 / 실제)
- (결함 2: …)
결함마다 회귀 테스트를 추가하고, 고친 뒤 전체 테스트를 다시 돌려라.
```

## 판단 반영 지시 (같은 빌드 세션)

수정 지시가 있으면 한 메시지에 이어 붙여 함께 보냅니다.

```
DECISIONS.md 판단기록의 A?~A? 답을 반영하라. 추천과 다른 답만 고치고 다른 부분은 바꾸지 마라.
항목마다 고친 파일:함수와 추가한 테스트를 그 항목의 `반영:` 줄에 적어라. 답·이유 줄은 고치지 마라.
설계가 바뀌면 DESIGN.md의 해당 줄과 `## 바뀐 점`도 고쳐라.
```
