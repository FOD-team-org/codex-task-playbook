# 검증 지시 (빌드와 다른 새 세션)

```
앱 코드는 수정하지 마라. counterexample-review 스킬로 REQUIREMENTS.md 각 항목의 위반을 찾아라.
DESIGN.md가 있으면 결함마다 설계의 어느 줄(흐름·파일 지도·요구사항 표)과 어긋났는지, 아니면 설계 자체가 틀렸는지 적어라.
요구사항 대조가 끝나면 security-check 스킬로 보안 결함을 따로 찾아라. 변이 검사는 빌드 때 한 결과(DECISIONS.md `## 검증`)를 읽기만 한다.
```

## 받은 뒤 할 일

- 결함마다 반례 행을 직접 열어 보고 채택/기각을 정합니다. AI 검증도 사실과 다른 지적을 할 수 있습니다.
- 채택한 것만 BUILD_PROMPT.md의 수정 지시로 넘깁니다.
- 채택/기각과 그 이유를 DECISIONS.md `## 검증`에 V번호로 남깁니다. 기각한 지적은 'AI가 틀렸던 순간'의 재료입니다.

## 제출 전 연습 (검증 세션, 수정이 끝난 뒤)

```
앱 코드는 수정하지 마라. DESIGN.md 설명 노트와 DECISIONS.md를 읽고 아래 유형으로 질문을 한 번에 하나씩 내라. 실제 파일·함수·수치를 넣고, 질문 하나에는 실제와 다른 전제를 섞되 어느 것인지 말하지 마라. 내가 답하면 맞은 점과 빠지거나 틀린 점을 파일:함수 근거로 두 줄 안에 알려 주고 다음 질문을 내라.
유형: ① 계산 방법(없으면 핵심 처리 규칙)을 고른 근거·버린 대안·한계 ② 데이터가 거치는 모듈과 상태 저장·소유 ③ 검증한 것과 가정한 것, 평가자가 확인할 경로 ④ 역할과 권한 경계(역할이 없으면 경계값 처리) ⑤ 자료·조건이 바뀌면 더 할 검증과 AI 결과를 믿은 근거 ⑥ 문제 기록 한 건을 어떻게 발견하고 AI 진단을 어떻게 판단했나
```
